# Project Persistence API contract v1

Status: conceptual; no routes are implemented by this document.

## Resource API

Project resources use the same `/api/v1` major prefix but a separate contract
family from computational operations:

| Method and route | Purpose |
| --- | --- |
| `POST /api/v1/projects` | Create a project at revision 1 |
| `GET /api/v1/projects` | List compact summaries |
| `GET /api/v1/projects/{projectId}` | Read the current project snapshot |
| `PUT /api/v1/projects/{projectId}` | Atomically replace name and schema using OCC |
| `DELETE /api/v1/projects/{projectId}` | Hard-delete a project |

`PUT` is chosen over `PATCH`: Save replaces the complete aggregate state the
workspace owns, which makes validation, dirty-state reconciliation and atomicity
unambiguous. A partial patch has no v1 use case. None of these routes invokes or
changes the Computational API contract.

All JSON object fields documented below are required and unknown fields are
rejected. Success and error responses use `application/json`, except `204`.
Timestamps use ISO 8601 UTC strings.

## DTOs

### CreateProjectRequest

```json
{
  "name": "Normalization exercise 1",
  "schema": {
    "schemaVersion": 1,
    "relation": {
      "name": "ENROLLMENT",
      "attributes": [
        { "id": "attr_a", "name": "Student ID" },
        { "id": "attr_b", "name": "Course ID" }
      ]
    },
    "functionalDependencies": [
      { "left": ["attr_a"], "right": ["attr_b"] }
    ]
  }
}
```

The server generates identity, revision and timestamps. It trims the project
name. It does not analyze the schema.

### ProjectResponse

```json
{
  "project": {
    "id": "12b98a42-87ce-48b8-8da2-c647f2f6b941",
    "name": "Normalization exercise 1",
    "schema": {
      "schemaVersion": 1,
      "relation": {
        "name": "ENROLLMENT",
        "attributes": [
          { "id": "attr_a", "name": "Student ID" },
          { "id": "attr_b", "name": "Course ID" }
        ]
      },
      "functionalDependencies": [
        { "left": ["attr_a"], "right": ["attr_b"] }
      ]
    },
    "revision": 1,
    "createdAt": "2026-09-09T14:30:00.000Z",
    "updatedAt": "2026-09-09T14:30:00.000Z"
  }
}
```

`POST` returns `201 Created` and this envelope; `GET` by ID and successful
`PUT` return `200 OK` with the same envelope.

### UpdateProjectRequest

```json
{
  "name": "Normalization exercise 1 — revised",
  "schema": {
    "schemaVersion": 1,
    "relation": {
      "name": "ENROLLMENT",
      "attributes": [
        { "id": "attr_a", "name": "Student" },
        { "id": "attr_b", "name": "Course ID" }
      ]
    },
    "functionalDependencies": [
      { "left": ["attr_a"], "right": ["attr_b"] }
    ]
  },
  "expectedRevision": 3
}
```

On success the complete name/schema replacement is atomic, `revision` becomes
4, `updatedAt` is generated by the server, and `createdAt` is unchanged. The
attribute IDs in the request and response remain unchanged.

## List contract

`GET /api/v1/projects?limit=20&offset=0` returns compact summaries:

```json
{
  "projects": [
    {
      "id": "12b98a42-87ce-48b8-8da2-c647f2f6b941",
      "name": "Normalization exercise 1",
      "relationName": "ENROLLMENT",
      "attributeCount": 2,
      "functionalDependencyCount": 1,
      "revision": 4,
      "createdAt": "2026-09-09T14:30:00.000Z",
      "updatedAt": "2026-09-09T15:05:12.000Z"
    }
  ],
  "pagination": {
    "limit": 20,
    "offset": 0,
    "total": 1
  }
}
```

`createdAt` is included: it is cheap scalar metadata and helps distinguish same-
named projects and explain their age. The schema body and computed normal forms
are excluded. Counts and `relationName` are read from the bounded JSON snapshot;
they are not independently persisted in v1.

Pagination uses `limit` plus `offset`: default limit 20, maximum 100, default
offset 0; both must be non-negative integers and `limit` must be at least 1. This
is adequate for initial volumes and supports an exact `total`. Cursor pagination
can replace it in a future compatible endpoint/query mode if scale demonstrates
the need. Default order is `updatedAt DESC`, with `id ASC` as a deterministic
tie-breaker. V1 has no search, filtering or caller-selected sort.

## Delete

A successful `DELETE` returns `204 No Content`. A missing project returns `404
PROJECT_NOT_FOUND`, including on a repeated delete. The operation is still HTTP-
idempotent because repeating it leaves the resource absent; idempotence does not
require identical response status. Delete is hard and has no response body,
tombstone or restore operation.

## Error family and mapping

Project API errors use the existing envelope shape but a separate
`ProjectErrorCode` type/catalogue. They are not added automatically to the
frozen computational `ApplicationErrorCode` union.

```json
{
  "error": {
    "code": "PROJECT_REVISION_CONFLICT",
    "message": "The project was modified after the requested revision.",
    "details": {
      "projectId": "12b98a42-87ce-48b8-8da2-c647f2f6b941",
      "expectedRevision": 3,
      "actualRevision": 4
    }
  }
}
```

| Project error code | HTTP | Meaning |
| --- | ---: | --- |
| `INVALID_PROJECT` | 400 | Invalid project/name/schema shape or invalid draft state |
| `PROJECT_NOT_FOUND` | 404 | No visible project has the supplied ID |
| `PROJECT_REVISION_CONFLICT` | 409 | `expectedRevision` differs from current revision |
| `PROJECT_LIMIT_EXCEEDED` | 422 | Project draft or list request exceeds a documented product limit |
| `PERSISTENCE_ERROR` | 500 | Unexpected persistence failure; no internal details exposed |

Malformed JSON/media-type/routing concerns may continue to use transport-level
`INVALID_REQUEST` where the shared HTTP adapter already defines it. Draft
validation may reuse internal validators and familiar detail names such as
`attributeId`, but public persistence failures use this small project catalogue.
In particular, computational codes such as `INVALID_ATTRIBUTE` and
`UNKNOWN_ATTRIBUTE_REFERENCE` are not leaked as Project API top-level codes;
their precise cause is represented in `INVALID_PROJECT.details` (for example
`reason: "UNKNOWN_ATTRIBUTE_REFERENCE"`, `field`, and `attributeId`). Limit
failures use `PROJECT_LIMIT_EXCEEDED`, never `ANALYSIS_LIMIT_EXCEEDED`.

Unexpected database availability, serialization and adapter failures map to
`500 PERSISTENCE_ERROR`. The client receives no SQL, table, driver, stack or
constraint names. Authentication/authorization mappings are deliberately
undefined until that contract exists.
