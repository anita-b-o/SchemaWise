# Project Persistence v1

Status: proposed contract, accepted design decisions; implementation is out of
scope for this tranche.

## Scope and boundary

Project Persistence v1 stores the editable state of a SchemaWise project. It is
separate from the frozen Computational API v1:

```text
Frontend -> Project Persistence API -> Application Layer -> Persistence Ports -> Database Adapter
Frontend -> Computational API       -> Application Layer -> Normalization Engine
```

The first path manages resources and state. The second remains deterministic,
stateless and unaware of projects. Application use cases may coordinate the two
paths in the future, but their DTOs, errors and side effects remain distinct.

This design does not add a database, ORM, migration, repository implementation,
route, authentication, frontend persistence, local storage or autosave.

## Project definition

A `Project` is the durable container for one editable normalization exercise:

- `id`: stable opaque identity generated by the server;
- `name`: the project display name, distinct from the relation name;
- `schema`: the current versioned draft snapshot, containing the relation and
  its functional dependencies;
- `revision`: persisted optimistic-concurrency version;
- `createdAt` and `updatedAt`: server-generated timestamps.

For example, a project can be named `Normalization exercise 1` while its
relation is named `ENROLLMENT`. Neither name identifies the other and neither is
used as a primary key.

`Project.name` is required. The server trims surrounding Unicode whitespace,
then requires 1 to 120 characters. It stores and returns that normalized value.
Duplicate project names are allowed in v1 because `Project.id` is the only
identity. Relation and attribute display names are not silently normalized in
the persisted schema; drafts must preserve exactly what the editor displays.

## Identity

`Project.id` is a server-generated UUID v4, represented as a JSON string and a
native UUID value in PostgreSQL. UUID v4 is preferred to a ULID because ordering
is already explicit through `updatedAt`, it has broad runtime/database support,
and it does not leak creation time. “Server-generated string” describes the API
type but is not by itself an identity format. Clients must treat the UUID as an
opaque token.

Relation names and slugs are mutable presentation values and must never be used
as project identity. No project slug is introduced in v1.

Attribute IDs have a different scope: they are logical identities inside a
project schema. IDs generated by the frontend, currently such as
`attr_<crypto.randomUUID()>`, must be stored and returned byte-for-byte. Loading,
renaming or saving a project must not regenerate them. Functional dependencies
reference these IDs, and preserving them is required for safe renames,
snapshots, diffs and possible analysis history.

## Aggregate and lifecycle

`Project` is the aggregate root. It controls its name, complete schema snapshot
and revision. Attributes and functional dependencies do not need database
identities in v1: they are small values that are validated and replaced within
the project boundary, are never loaded independently, and are not queried as
standalone resources.

The v1 lifecycle is `create`, `read`, `list`, `update` and `delete`. Archive and
soft delete are excluded. Delete is a hard delete because there is no retention,
restore, audit or ownership requirement yet; inventing tombstone semantics now
would add policy without a product use case.

## Draft versus computational validity

Saving and analyzing are different operations. Project Persistence accepts a
structurally coherent draft that may not yet be analyzable, including:

```json
{
  "schemaVersion": 1,
  "relation": { "name": "", "attributes": [] },
  "functionalDependencies": []
}
```

Draft validation therefore permits an empty relation name, zero attributes and
blank attribute display names. This matches the frontend's initial workspace.
It still rejects malformed data, unknown properties, invalid or duplicate
attribute IDs, over-limit collections/strings, duplicate IDs within an FD side,
and every FD reference to an attribute ID absent from the same snapshot.

Computational validation remains stricter: before invoking the engine it
requires a nonblank relation name, one or more attributes and valid nonblank
attribute names, together with all existing computational invariants. A saved
draft is not evidence that it can be analyzed. Shared validation primitives for
DTO shape, IDs, references and limits should be reused, with separate
`validateProjectDraft` and `validateComputationalSchema` entry points. Project
Persistence must not construct engine objects merely to validate a draft.

## Derived results

V1 persists only project metadata and the schema draft. It does not persist
`AnalysisResponse`, candidate keys, minimal cover, normal-form results,
explanations, 3NF synthesis, BCNF decomposition, dependency-preservation output
or attribute closures. These values are deterministic, small enough to
recalculate, and invalidated by every schema change; storing them would duplicate
derived state and couple persistence migrations to engine output contracts.

Possible future resources include an immutable `ProjectVersion`, `Snapshot` or
`AnalysisRun` associated with a specific project revision and engine version.
The aggregate ID, preserved attribute IDs, internal schema version and monotonic
revision leave room for that extension. No speculative tables are defined now.

## Ownership and implementation order

V1 design has no owner. It does not add a nullable `owner_id` or a fictitious
user because both would encode authentication semantics before they exist.
Ownership should be added in the migration and contracts that integrate Project
Persistence with authentication.

Database CRUD, the adapter and application use cases may be implemented and
tested before authentication. Project HTTP routes may be exercised locally or
in isolated tests, but must not be publicly exposed in production until requests
are authenticated and every operation is scoped by ownership. This ordering
lets persistence behavior mature without turning unowned IDs into an access
control mechanism.

## Frontend implications (future)

The minimum future UI is: New project, editable project name, Save, an explicit
Saved/Unsaved state and Open projects (a simple switcher/list is sufficient).
No dashboard, collaboration model or sync protocol follows from v1.

The current workspace `revision` is a local session counter used to bind
computations to draft snapshots. Rename it conceptually to `draftRevision` when
persistence is integrated. `project.revision` is the last server revision used
for optimistic concurrency. Local edits increment `draftRevision`, not
`project.revision`; only a successful save replaces the latter with the server
response. Dirty state means the local draft/name differs from the last loaded or
saved project snapshot, not merely that the two counters differ.

Manual Save is required before autosave. It makes conflict timing and user intent
visible, avoids retry/debounce complexity, and is appropriate while ownership
and recovery UX are not present.

## Migration and evolution requirements

Future PostgreSQL migrations must be ordered, version-controlled, reviewable,
repeatable in a clean database, transactional where PostgreSQL permits, and
tested both from empty state and from the immediately previous schema. The tool
must support explicit SQL escape hatches, JSONB, UUID, `timestamptz`, checks and
indexes without forcing engine or HTTP DTOs into generated persistence models.

Backups and restore are deployment concerns, but schema evolution must never
rewrite JSON blindly: readers select by `schemaVersion`, migrations transform a
known version to the next version, and unknown versions fail safely. Migration
scripts require pre-migration backup/restore planning once production data
exists.

## Open questions

There are no blocking product-model questions before implementing the
persistence layer. Public deployment remains blocked on the separate ownership
and authentication design. Choice of migration/query tooling is the next
implementation decision, not an unresolved contract decision.
